Model partition

Large models take long to run because one processor core does most of the work. Tools ▸ Partition ▸ Partition Model splits the model into sub-models along the flow, so that the coupled parallel simulation can run them at the same time on several cores. You enter only the number of partitions – or let Detect and OPT choose it for your computer; the cut points are found automatically. Model partition is part of the HPS (High Performance Simulation) edition.

How the model is split

  • One direction of flow per partition. The flow directions come from the base results (the results loaded when you partition). Every partition drains towards its own outfalls or towards one downstream partition; water never flows back and forth across a cut.
  • Only conduits are cut, and only where it is safe. Pumps, orifices, weirs, outlets and the links of flow dividers are never cut. Pipes with oscillating flow (flow that changes direction during the run) are not cut, and ponding areas – manholes that flood onto the same surface – stay in one partition.
  • Balanced and few cuts. The partitions get about the same amount of work (within the size tolerance) with as few cut points as possible, because every cut point is exchanged in every iteration of the run. After Detect, partitions on slower cores get less work.

At a cut point the pipe stays in the upstream partition. In the upstream sub-model its downstream end becomes a boundary outfall; in the downstream sub-model the node receives the pipe's flow. During the coupled run the two sub-models exchange flow and water level at every iteration, so they behave like one model.

Before you start

  • Save the model. The sub-models are written next to it.
  • Run the model once (the whole model) and keep these results loaded (or open a run from the Database). Without results the pipe directions as drawn are used and oscillating flow is not checked. For 1D-2D models use 1D-2D results, so that the ponding areas on the surface are known.
  • Decide on which computer the coupled run will take place. The best number of partitions depends on its processor; use Detect on that computer.

The Model Partition panel

Click Tools ▸ Partition ▸ Partition Model. The panel opens over the map with two tabs, Partition and Regenerate. The Partition tab has five numbered sections that you work through from top to bottom:

Partition the model, step by step

  1. Open the panel (Tools ▸ Partition ▸ Partition Model).
  2. On the computer that will run the model, click Detect once (about 10–20 s). The number of partitions is set to the best value for this processor. Without Detect, type the Number of partitions yourself.
  3. Check Base results: it names the results file used for the flow directions.
  4. Click Partition. After a moment the map shows the partitions in colour and section 2 Result shows the counts and one row per partition.
  5. Look at est. speed-up. Click OPT to let Avaris2 CS try several numbers of partitions and take the fastest (below).
  6. Read 4 Checks. Fix ✗ errors; read the ⚠ warnings.
  7. Optionally adjust the result: split the slowest partition, merge two small ones, or move a cut point (Adjust).
  8. In 5 Generate sub-models, choose the folder and click Generate N Sub-models.
  9. Run the model with Simulation ▸ Run ▸ Coupled parallel (Coupled parallel simulation).

Detect: balance the partitions for this computer

Modern processors have cores of different speed – for example Intel processors with performance cores (P-cores, two threads each) and slower efficiency cores (E-cores). Detect measures this once and the partition then follows it:

  1. Click Detect in 1 Settings. Avaris2 CS reads the processor (kinds of core, threads) and runs a short built-in benchmark model on every kind of core, first one sub-model per core, then one per thread, all at the same time.
  2. The green box shows the processor, how many cores of each kind it has, the relative speed of each kind (fastest = 1.00, and the speed when both threads of a core are busy), and Set for this computer: N partitions.
  3. The number of partitions is set to N. If the processor has fast and slower cores, the box also says how many nodes go on each fast core and on each slower one: partitions for the slower cores are made smaller, so that all finish each time step at about the same moment.
  4. Click Partition (or Partition Again) to apply it.

The measurement is stored with your Avaris2 CS settings and is valid only on this processor. On another computer the box says that the profile was measured on a different processor – click Detect there. Until then the partitions are balanced by number of nodes.

Tip:

You can always type a different number of partitions, also more than this computer has cores – for example when the coupled run will take place on a larger computer. Nothing is blocked: the partitions then get the same size and a hint reminds you to run Detect on that computer.

OPT: find the fastest number of partitions

The best number of partitions depends not only on the processor but also on the model: groups that must stay together (ponding areas, pumping stations, oscillating pipes) can make one partition much larger than the others, and more partitions mean more cut points. OPT tries this out:

  1. Partition the model once (OPT appears in the est. speed-up box after Detect).
  2. Click OPT. Avaris2 CS partitions the model for several numbers – the number of cores and one more and one less, a number between cores and threads, the number of threads, the number from Detect and the current number – with the settings of the panel. A bar shows the progress; each number takes about as long as one Partition. Cancel stops.
  3. The table lists for each number: Cut points, the Largest partition, the Max load and the Est. speed-up. The fastest is marked fastest and selected; the current number is marked (current).
  4. To choose, the cut points count as extra work (each sub-model costs 1 % for the exchange, each cut point a little more), so a number with many more cut points but almost the same speed-up is not chosen. Click another row if you prefer it.
  5. Click Use N Partitions. The partition already computed for that number is taken at once – there is no need to partition again.

When the largest partition stops getting smaller as the number of partitions grows, OPT says why under the table: a group of N nodes is kept whole – for example a ponding area or a pumping station with its wet well – and that group blinks on the map. More partitions do not run faster then. To allow cuts there, look at the Advanced settings (for example untick Keep ponding areas whole, or raise the 2D ponding depth) and partition again.

Map markings and legend

While the panel is open the map shows the partition colours, the cut points (red ⊗; orange when on a pipe with oscillating flow), pipes that are not cut (purple dashed) and ponding areas (blue dashed circles), with a legend at the bottom right. These markings are shown whatever the layer visibility. The eye button at the top left of the map (or T) hides and shows them together.

Adjust the result

Section 3 changes the partition by hand. Every change can be undone with Undo (one step per change), and the result, the checks and the map update after each change.

Split Partition

Use it when one partition is too large – for example the one with the highest load.

  1. Click the partition's row in the table (it is highlighted on the map).
  2. Click Split Partition…. The dialog shows the partition's nodes and cut points and suggests a number of parts so that each part has about the target size.
  3. Change Split into if needed. The rules (flow counts, oscillating flow, ponding areas) are those of the main partition and can be changed for this split only.
  4. Click Preview. The new parts are shown on the map and in a table with their nodes and cut points; the line below gives the number of new cut points, whether they are all one-way in the base run, and the estimated speed-up before → after.
  5. Click Apply, or Cancel to leave everything as it was.

The other partitions and their cut points do not change. The split partition keeps its number and the new parts get the next free numbers. If the partition cannot be split as set, a message names the groups that must stay together (they blink on the map) and offers the largest number of parts that is possible, or Change Settings.

Merge Partitions

  1. Click Merge Partitions….
  2. Choose the first partition and the adjacent one to join it. Only partitions that share a cut point can be merged; the two smallest adjacent partitions are suggested.
  3. Click Merge. The higher number is joined into the lower one.

Move Cut and Add Cut

These never change the number of partitions; only the boundary between two neighbouring partitions moves.

  • Move Cut…: click a cut point ⊗; the conduits nearby where the cut may go blink; click one. Only the two partitions next to it change.
  • Add Cut…: click a conduit; its upstream branch joins the neighbouring partition. It is refused, with the reason, if it would create a new partition or cut a pump, weir or similar; you are warned for oscillating flow and ponding areas.

Press Esc or click Finish when done.

After the model changes: Regenerate

When you edit the master model after partitioning, the sub-models are out of date and the coupled run is blocked until they are updated. Open Partition Model ▸ Regenerate:

  • the saved partition is applied to the changed model: existing nodes keep their partition, new nodes join the partition downstream of them (else upstream, else the nearest);
  • the changes since the last generation are listed, with the sub-models that must be rewritten;
  • only the changed sub-models are written again. Sub-models that were edited directly are detected, and you are asked before they are overwritten.

If the network changed a lot (new trunk sewers, many new branches), partition again instead.

Coupled parallel simulation

A coupled parallel run starts one engine process per sub-model. All sub-models take the same time step and exchange flow and water level at the cut points in every iteration, so the result is that of the whole model – computed on several processor cores at once. It works for 1D models and for 1D-2D models.

Run it

  1. Partition the model and generate the sub-models (Model partition).
  2. Click Simulation ▸ Run. In the Run section of the dialog choose Coupled parallel. It shows the number of sub-models and cut points, and a speed hint for this computer.
  3. Enter a name and click Run. The progress dialog shows the overall progress; Stop ends all sub-models.
  4. When the run ends, the Run Status dialog shows the run mode, the run time, the continuity errors and the convergence, and – under Sub-models – the timing of every sub-model.

The results of the sub-models are merged into one results file and one report of the whole model, under the run name. Everything works as after a normal run: map, themes, flags, profiles, graphs, report, CSO statistics, 2D analysis and comparison. In the Database the run type is 1D coupled or 1D-2D coupled, and the run summary shows the run time. Deleting such a run in the Database also deletes its sub-model folder <run>_parts.

Cores: automatic binding

Every coupled run binds the sub-models to the processor cores automatically – you do not choose anything:

  • the largest sub-model (nodes and 2D cells) runs on the fastest core, the next largest on the next fastest, and so on;
  • one sub-model per physical core; the second thread of a core is used only when there are more sub-models than cores;
  • Windows power throttling is switched off for the engine processes, so that Windows does not move them to the slow cores.

The binding follows the current sizes of the sub-models, so it needs no earlier run. With more sub-models than logical processors the binding is left to Windows.

Run Status: timing of the sub-models

Open Sub-models in the Run Status dialog. For each sub-model it lists the nodes, the computing time, the waiting time (time it waited for the others in every step) and the core it ran on. The headline names the sub-model that computes longest and the use of the cores (100 % = no waiting). The sub-model with the longest computing time sets the speed of the whole run: make it smaller with Split Partition, or partition again with OPT.

1D-2D models

When 2D flooding is enabled and the mesh exists, the coupled run is a 1D-2D run. The mesh is shared out over the sub-models when the run starts (cells inside a partition's area go to it, the others to the partition of their manholes or nearest neighbours), so you do not need to generate the sub-models again after rebuilding the mesh. 2D links that cross a partition boundary are exchanged in every iteration like cut pipes. Both mesh types (square grid and unstructured mesh) are supported.

Hot start files and data files

  • USE HOTSTART: when the model starts from a hot start file of the whole model, the file is split per sub-model when the run starts (objects are matched by ID; boundary outfalls and 2D cells that the whole model did not have start empty). The split files are written to the run's _parts folder; the original file is not changed. SAVE HOTSTART of a sub-model is written there too.
  • Rain gage files, time series files, the temperature file and the files of the [FILES] section may be given with relative paths (for example ../rain.dat): they are resolved from the folder of the sub-model, also for the copies written to the _parts folder.
  • Long node IDs are fully supported.

Speed

  • Use Detect and OPT on the computer that runs the model. As a rule, at most one sub-model per physical core; the second threads add little.
  • Each sub-model needs enough work: with very small sub-models the exchange costs more than it saves. Large models (tens of thousands of objects) gain the most.
  • Look at the Run Status timing: high waiting times on all sub-models but one mean that one is too large.
  • Close other heavy programs during the run.

Example on a 2-core computer: Riverside (593 nodes) – whole model 12.9 s, 2 sub-models 8.6 s. Riverside 1D-2D (1,578 cells) – whole model 133 s, 2 sub-models 95 s. Gains grow with the model size and the number of cores.

Accuracy

The sub-models solve the same equations as the whole model and the convergence check is global, so the results match the whole model closely: on the Riverside example the largest difference in max. node depth was 1 cm (2D cells 3 mm), and the continuity error was the same. The remaining differences are of the size you also get from changing the routing step of the whole model slightly. To check a model of your own, run it once as a whole and once coupled, and compare the two runs in the Scenario Comparison – the KPI cards include the run time.

Note:

If the master model was changed after partitioning, the Coupled parallel option is disabled and the dialog says why. Use Regenerate in the partition panel.
